背景

fastblog（原 StaticGen）是一个静态博客生成器：在 content/ 目录撰写 Markdown，一条命令即可渲染为完整的静态 HTML 网站。本次目标是把它 部署为个人博客 blackholemax-oss.github.io，并让部署流程沉淀进 工具的 deploy 命令。

部署方案选型

最初考虑两种思路：

  1. 源码入库 + CI 自动构建：把生成器源码与文章推送到 main 分支， GitHub Actions 每次 push 后安装依赖、构建并发布到 gh-pages。
  2. 产物仓库 + GitHub Actions 发布：blackholemax-oss.github.io 只包含静态网页文件与 .github/workflows/pages.yml，Pages 构建源 选择 GitHub Actions，每次推送产物自动重新发布。

最终选择了方案 2：产物仓库干净、不含生成器源码，符合"博客仓库只 存放站点内容"的直觉；发布链路简单，一条 deploy 命令完成 构建、恢复工作流、提交、推送。

实施过程

建仓与 Pages 配置

  • 用 gh repo create blackholemax-oss.github.io --public 创建公开仓库 （GitHub Pages 用户站点要求公开）。
  • 本地以 github-io 为远程名推送 main，保留 fastblog 自身的 origin 不动。
  • 通过 gh api 把 Pages 构建源从 legacy 切换为 workflow。

pages.yml 工作流

产物仓库内的工作流采用 GitHub 官方 Pages 发布模式：

on:
  push:
    branches: [main]

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  deploy:
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - uses: actions/checkout@v4
      - name: Remove workflow files from site
        run: rm -rf .github
      - uses: actions/configure-pages@v5
      - uses: actions/upload-pages-artifact@v3
        with:
          path: .
      - id: deployment
        uses: actions/deploy-pages@v4

上传前先删除 .github 目录，避免工作流文件被发布到站点。

踩坑：build 清空输出目录

build 每次清空 output/，首次发布后发现 pages.yml 被连带删除。 解决办法是把恢复工作流的逻辑内置进 deploy 命令：推送前检查 output/.github/workflows/pages.yml，缺失时按内置模板自动写入， 彻底避免手动恢复。

deploy 命令改造

新 deploy 流程：构建 → 恢复 Pages 工作流 → 提交全部变更 → 强制推送到配置的远程分支（github-io/main）。

配置也随之调整：

deploy:
  remote: "github-io"   # 产物仓库的远程名
  branch: "main"        # 推送目标分支（配合 GitHub Actions 自动发布）

同时移除了旧的 auto_actions 工作流生成逻辑——产物仓库模式不再 需要生成构建型 workflow。

品牌改名：StaticGen → fastblog

仅改动品牌显示名（CLI 描述、--version、项目名常量、README、 主题元数据、站点页脚），模块名 staticgen 与 python -m staticgen.cli 入口保持不变，避免破坏导入链。

发布链路

.venv-win/Scripts/python.exe -m staticgen.cli deploy

构建 → 推送 → GitHub Actions 自动发布到 Pages，整个过程约半分钟。

结语

本次改造让「写作 → 部署」收敛为一条命令：写文章、deploy、 等待 Actions 发布即可。后续计划：更多文章、主题定制与归档页。
